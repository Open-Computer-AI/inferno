# Attestation timing breakdown — 26 October 2026

## What was measured

Low-rate, sequential HTTP measurements with one request in flight per runner.
The principal AWS sample window was 04:06:59–04:08:27 UTC (09:36:59–09:38:27 IST).
These windows use first/last recorded response timestamps. The on-Air control
followed at 04:08:33–04:08:44 UTC. Pooling and packet-metadata
experiments were separate, later rounds; their values must not be combined into
one simultaneous experiment.

There were **157 timed HTTP requests: 92 proof requests and 65 health requests**.
All returned HTTP 200 and the expected envelope. Envelope validation is not an
independent cryptographic verification by the upstream provider; uniqueness was
not measured in this timing round. Proof bodies, hashes and credentials were not
retained. Monotonic clocks measured durations within each host. No cross-host
wall-clock subtraction was used to invent one-way network timings.

Production configuration stayed unchanged: helper limit 16, AWS queue concurrency
16, and upstream connection reuse off. No production helper, queue or gateway
restart was performed. Temporary queue copies bound only AWS loopback 19395.
One password-authenticated SSH session measured the Air's existing helper locally;
it installed no key and closed afterward. The local askpass helper was removed.

## Where the measured time goes

### Client-side phases, production queue proof path

| Phase | Median over the 12 primary samples |
| --- | ---: |
| Connect to AWS loopback queue | 0.22 ms |
| Serialize/send HTTP request | about 0.10 ms |
| Wait for complete response headers | about 840 ms |
| Read remaining buffered body after headers | about 0.02 ms |

These independently aggregated medians do not sum to an exact individual-request
waterfall. Header wait includes the queue, forwarding/channel setup, network,
Air work and return path. Body-read time starts after headers arrive; it does not
measure the entire on-wire body transmission, since bytes can already be buffered.

**The tiny TCP connect number is not AWS-to-Air connection time.** Both AWS queue
19095 and SSH forwarding listener 19085 are local sockets. Remote SSH channel
establishment occurs after that local TCP accept and contributes to response wait.

The helper HTTP URLs use literal loopback addresses and established SSH/Tailscale
transport, so these HTTP calls do not perform external DNS resolution or a new TLS
or SSH login handshake for each proof. New forwarding channels still have a cost.
This report excludes public API TLS, account selection, session setup and audio.

### Instrumented queue copy: 24 health/proof requests, no contention

The actual deployed queue source was hash-checked and executed in a separate
process-local module. A thread-local timing wrapper instrumented that copy only.

| Component | Median | Maximum |
| --- | ---: | ---: |
| Admission semaphore wait | **0.0054 ms** | 0.0204 ms |
| Handler processing excluding admission and upstream forwarding | **0.0414 ms** | 0.0779 ms |
| Whole local queue wrapper, client total minus upstream duration | **1.225 ms** | 1.648 ms |
| Upstream local TCP connect to SSH listener | 0.198 ms | 0.319 ms |

Every instrumented request needed one forwarding attempt. No busy retries,
unreachable retries or failures occurred. The approximately 1.2 ms wrapper figure
includes local TCP/HTTP/framework/instrumentation overhead; 0.04 ms is only the
handler portion. These are not production-queue internal traces, and do not prove
admission wait stays small when more requests arrive than its concurrency limit.

## Connection reuse experiments

### Direct helper connection: primary paired round

Across 12 paired proofs, fresh minus reused time averaged **547.634 ms**, with a
descriptive bootstrap 95% interval of **501.726–595.704 ms**. The paired median
saving was 545.455 ms. All 12 differences favored reuse.

### Existing queue option: separate paired round

A separate in-memory queue copy alternated its existing `KEEPALIVE` option after
each completed request. Production's environment was not changed. A health request
seeded the pool before the 12 proof pairs. Order alternated between pairs.

| Queue-copy mode | Proof samples | Median | Maximum | New upstream connections |
| --- | ---: | ---: | ---: | ---: |
| Reuse off | 12 | **671.564 ms** | 1,064.384 ms | 12 |
| Reuse on | 12 | **278.516 ms** | 678.508 ms | 0 |

Mean paired saving was **328.081 ms**, descriptive bootstrap 95% interval
**262.805–415.192 ms**. The paired median saving was 282.748 ms; all 12 differences
favored reuse. Median differences and medians of paired differences are different
statistics. The two experimental rounds occurred at different times, so their
different fresh-connection costs should not be treated as a contradiction or
combined into one fixed saving.

The observed proof response was 4,180 bytes with Content-Length framing, no chunked
encoding, and an open connection. The queue's existing safe-reuse conditions
accepted it. This reuses a connection, not a proof. Subsequent POSTs still forward
to the helper. These timing samples do not establish proof uniqueness.

The deployed queue's `QUEUE_KEEPALIVE` variable was absent, so its effective value
remained the source default **off**. The supported option is a candidate for a
separate sustained qualification; it was not enabled in production. Pool idle
expiry is 10 seconds in the verified queue source, so this does not promise warm
latency after a long idle interval. Stale-connection and reconnect behavior needs
its own production promotion gate.

## Network and encrypted SSH packet observations

- Six Tailscale pings all used DERP(blr): 219, 220, 223, 224, 225 and 242 ms;
  median **223.5 ms**. This is a Tailscale ping measurement, not an HTTP phase.
- The production SSH TCP socket reported smoothed RTT about 246–253 ms.
- A bounded ten-second tcpdump retained **metadata text only** for the encrypted
  Air/AWS SSH connection: timestamps, addresses and TCP payload lengths. No PCAP,
  HTTP headers, bearer tokens, decrypted proof data or packet payload dump was saved.
- During that trace, fresh proof 1 took 1,691.127 ms, reused proof took 300.859 ms,
  and fresh proof 2 took 553.508 ms. All succeeded.
- The capture's exit 124 was its intended ten-second timeout, not an HTTP error.
- In the slow first sample, a 100-byte AWS→Air encrypted packet was followed by
  Air's 52-byte reply about 229 ms later. A subsequent request-sized AWS packet
  was acknowledged, then about **1.20 seconds** passed before the first response-
  sized incoming data. SSH message types were not decrypted, so exact channel
  semantics are inferred rather than directly observed.
- AWS's outgoing SSH retransmission counters stayed at the same historical
  5,748 bytes / 58 retransmissions during this short trace. This does not rule out
  Air-side loss, underlying relay TCP behavior, or retransmissions in the earlier
  aborted load attempt.

The low-rate slow sample shows that high concurrency is not necessary to observe
a long fresh request. The trace alone cannot assign the silent interval to relay
delivery, SSH scheduling, the Air helper/Node or the native service. Simultaneous
Air-side request timing for that same request would be needed for that attribution.

These results do not isolate **incremental Tailscale overhead versus the former
public route**. Geographic RTT and SSH forwarding also existed on the public path.
No public SSH allowlist was opened for these measurements. The earlier controlled
public/private comparison is recorded separately in `LATENCY-20261026.md`.

## Budgets and the earlier aborted load

The deployed consumer has an **8-second whole-request HTTP timeout**. The verified
queue source uses a 25-second queue loop budget, 15-second upstream socket timeout,
50 ms busy-retry pause, and up to 6 seconds of unreachable retries spaced 250 ms
apart. These budgets are not additive guarantees. The queue loop's deadline does
not preempt an already-running upstream call; the caller can time out first.

Current helper source additionally defines a 7-second handler context, a 2-second
warm Node attempt and a 5-second one-shot fallback budget, with at most two fallback
processes. Those are **source-reviewed limits**, not new runtime-binary timing
measurements. The installed binary's serialized Node queue had already been
verified; pure native execution and fallback timing were not instrumented here.

The earlier production proof took 2,173.8 ms and breached the conservative **2-second
test guard**, not the 8-second caller deadline. Candidate 16-load tail reached
5,451.8 ms p99 / 5,874.3 ms maximum while the controller stopped and drained the
run; those are stop-period tail observations, not a completed steady-state
300-second baseline. Queue failures did not
increase. The timing work identifies substantial ordinary connection/forwarding
cost but does **not** establish the specific cause of that earlier event.

**32/33 sustained qualification remains incomplete. Production stays at 16.**
Connection reuse must be qualified under sustained load, idle/reconnect conditions
and production-health monitoring before any capacity or production change.
