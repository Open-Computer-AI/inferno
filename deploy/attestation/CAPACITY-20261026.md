# Concurrent attestation qualification — 26 October 2026

## Decision: do not raise production to 33

The planned test was an isolated 16-request reference, then 32 and 33 synchronized
bursts and five-minute closed-loop stages. The 16 sustained reference triggered a
safety stop after 25.085 seconds. **32 and 33 were not attempted.** This does not
establish a maximum safe concurrency; qualification remains incomplete.

Production remained at helper default 16 and `QUEUE_CONCURRENCY=16`. Its helper
PID 98414, queue PID 1038746 and gateway PID 481177 stayed unchanged. No production
restart, configuration change, database change or firewall change was made.

## Isolation and safety

- A separate instance of the exact installed helper binary ran on Air loopback
  19385, with a fresh owner-only token and a dedicated SSH reverse tunnel.
- A copy of the actual deployed queue source ran on AWS loopback 19395, forwarding
  to 19385, with production's `QUEUE_KEEPALIVE=0` setting.
- The test used a separate forwarding key restricted to the Air tailnet address,
  AWS listener 19385, and a 30-minute expiry. Host keys and SSH identities were pinned.
- Independent monitoring checked production health and a low-frequency production
  proof. Those probes are excluded from candidate proof counts and timings.
- Candidate requests used fresh HTTP connections, no client retries, an 8-second
  socket timeout, proof-envelope validation and in-memory uniqueness hashes.
  No proof body, hash, token or provider credential was retained in results.
- The probe had an independent process deadline and stopped scheduling on bad or
  stale Air telemetry, resource warnings, production degradation or candidate errors.
- The explicit latency guards were production health/proof below 2 seconds and
  candidate individual responses below 4 seconds. These are conservative qualification
  thresholds, not the application's 8-second deadline or a claim of customer failure.
- The test helper shared the physical Air, network and native services with production.
  This is process/port isolation, not independent hardware isolation.

Before load, setup-only readiness and teardown passed. Induced Air termination
before startup and AWS termination after temporary-key installation were checked.
Failure status propagated to the controller; ports, keys, files and children were
verified after cleanup.

## Recovery and remaining uncertainty

All candidate Go/Node/tunnel/queue PIDs were gone after cleanup. Air/AWS candidate
ports were closed, temporary roots removed, and the temporary AWS key absent.
Production subsequently passed 8/8 health checks at 470–604 ms with its failure
counter unchanged. Five direct Air proof probes took 24.86–31.28 ms.

Both tailnet endpoints reported a relayed path with an empty direct peer address.
The private route therefore contributes substantial baseline latency compared with
direct Air calls. This is **not proof that the relay caused this particular spike**.
The production SSH tunnel error log had not changed during the load window; its
older connection-timeout lines are not evidence of a new tunnel outage.

Correlated generation duration, channel/connect errors and transport timing are
needed to distinguish native serialization, shared network/relay variation and
forwarding retries. The temporary helper/tunnel's stderr was discarded in this
attempt, limiting retrospective attribution. Do not rerun higher load or promote
33 from this evidence.

## Why there are multiple concurrency limits

AWS queue concurrency controls how many requests are forwarded simultaneously;
excess requests wait there. The Air helper admission limit protects the helper;
excess requests receive 429, which the AWS queue can retry.

The installed binary also embeds a warm Node promise queue that serializes native
DeviceCheck work. Raising both outer limits to 33 would permit 33 concurrent
requests in the pipeline, not 33 simultaneous native operations. More concurrency
can hide network latency, but cannot remove native service-time or deadline limits.
33 is a requested configuration target, not an established hardware maximum.

## Production promotion remains separately gated

The current Go consumer makes one remote HTTP call with an 8-second timeout.
Restarting the AWS queue can refuse a request before the queue's own retry logic
accepts it. A momentarily quiet `in_flight=0` is not an admission barrier.

Before any production change, qualify the intended load, verify an admission/drain
mechanism or obtain an explicit controlled maintenance window, and prepare a
coordinated rollback covering both the Air helper and AWS queue. The existing
tunnel-only rollback guard cannot restore a partial helper/queue capacity change.

## Probe source and local verification

`capacity_controller.py` runs the two temporary supervisors; `capacity_air.py`
owns candidate helper/tunnel lifecycle and resource samples; `capacity_aws.py`
owns the candidate queue, production monitoring and staged probe runs.
`capacity_probe.py` emits only timing/status/count summaries.

The controller is intentionally restricted to the audited operator SSH identities,
host pins, Air/AWS hosts and isolated test ports. Its owner-only configuration is
kept outside Git. It cannot change production concurrency.
